> 陛下上朝，御膳房候旨。
> 用麦当劳官方 MCP 的真实数据，配上二十四节气的东方意境，做一份**你说了算**的点餐参谋。

## 一、它解决什么问题

点麦当劳时真正烦的不是"买不到"，而是三件事：

1. **选择困难** —— 菜单上百个 SKU，不知道今天该吃啥。
2. **算不清账** —— 套餐、券、随单购混在一起，不知道哪套最划算。
3. **没情绪价值** —— 点餐是纯功能操作，毫无期待感。

御膳房的解法：

| 问题 | 解法 | 依据 |
|---|---|---|
| 选择困难 | 「麦历呈报」按二十四节气/传统节日给当日主题 + 按预算口味打分排序 | 天文算法 + 官方真实菜单 |
| 算不清账 | 「户部精算」本地粗筛候选 → 官方 `calculate-price` 核价 | 官方核价结果，不自己加价 |
| 没情绪价值 | 宫廷语境交互 + 「今日宜尝鲜」娱乐彩蛋 | 纯文案，**不预测吉凶、不影响消费决策、不冒充官方促销** |
| **光看文字没食欲** | 「御膳图鉴」逐道调 `query-meal-detail` 取官方餐品图，先上图再谈价 | 官方 CDN 原图，不加工不代存 |

## 二、创意亮点

1. **节气不是噱头，是能算准的。** 二十四节气用 `ephem` 计算太阳视黄经（相对当日平春分点）求交节时刻，换算到 UTC+8。已用权威分至点数据对 2025、2026 年 8 个分至点交叉校验，**误差 ≤ 1 分钟**。传统节日用农历换算，与国务院办公厅 2026 放假安排**四点交叉验证全部吻合**（春节 2/17、端午 6/19、中秋 9/25、除夕 2/16）。

2. **严格区分"文化灵感"与"官方活动"。** 奏折里节气主题和麦当劳官方活动日历**分栏展示**，明确写着"臣未将二者混为一谈"。市面上很多作品会把节气文案包装成官方促销——这在合规上是红线。

3. **先本地筛，再官方核价。** 借鉴优秀 MCP 项目思路：本地按预算/偏好/主题打分取前 6，只把少量候选交给 `calculate-price`。减少无效调用，也避免把组合爆炸丢给 MCP。

4. **不编造是硬约束，不是口号。** 60 项测试里有专门用例守着：空菜单、未返回价格、未核实的券、核价失败、主题商品不可售、外送缺 `beCode`、地址簿为空……每一种都必须如实说"查不到"，而不是编一个出来。

## 三、主要功能

| 模块 | 做什么 | 数据来源 |
|---|---|---|
| `opening` | 陛下上朝：问候 + **三问一卡**（何膳 / 用度人数 / 传膳与送处），一轮点完 | 本地规则 |
| `date_context` | 日期 / 节气 / 传统节日 / 法定节假日识别，缺失降级 | 本地数据文件 + 天文算法 |
| `theme_rules` | 当日主题文案 + 「今日宜」娱乐彩蛋 | 本地规则 |
| `preference_profile` | 陛下旧例：明示偏好 vs 系统推测，可清除、可存档 | 本地存档，跨会话有效 |
| `menu_matching` | 真实菜单 → 候选方案（预算/偏好/主题打分） | MCP `query-meals` |
| `coupon_optimizer` | 优惠候选本地粗筛，未核实条件一律标注 | MCP `query-store-coupons` |
| `price_verification` | 官方核价核验，区分"已核验"与"估算" | MCP `calculate-price` |
| `recommendation_output` | 古风奏折渲染 + 合规自检 | 本地 |
| `scene_router` | 用餐场景路由：到店自取 / 麦乐送外送；外送多两道前置（地址 → 可配送门店 `beCode`） | MCP `delivery-query-addresses` / `delivery-query-stores` |
| `preference_profile` 持久化 | 陛下旧例可跨会话存档（存于 `~/.workbuddy/user_data/`，**不进仓库**） | 本地文件 |
| `meal_photos` | 御膳图鉴：逐道取官方餐品图（菜单列表不返回图片） | MCP `query-meal-detail` |
| `coupon_claim` | 代领券令编排：复述 → 确认 → 回查卡包 → 核价；声明「只能全领不能挑」 | MCP `auto-bind-coupons`（**确认后**） |
| 可领券令 | 解析官方「可领取」券并展示，标注非本单可用 | MCP `available-coupons` |
| `order_placement` | 代下单编排：**三重复述**（订单内容 / 金额明细 / 交付方式）全部点头才出单，只出**待支付订单** | MCP `create-order`（**三重复述后**） |

### 「让陛下点，不让陛下打字」是怎么落地的

引擎只产结构化选项，**不负责呈现**——呈现交给宿主的提问工具：

```
python scripts/imperial_kitchen.py opening                       # 三问一卡（默认）
python scripts/imperial_kitchen.py opening --single              # 降级：只呈第一问
python scripts/imperial_kitchen.py picks --stage <阶段>           # 后续各阶段
```

**开场一轮问完三问**（陛下反馈"一个个问效率太低"）：① 今日想用何膳（原四项，前两项固定）
② 用度与人数（预设档位，全可点；要自定走卡片「其他」）③ 传膳方式与去处（外送 / 自取 + 地址）。
把返回的 `questions` **整组**填进 `AskUserQuestion` 的 `questions` 参数，一次呈出三问，不拆多轮。

单问返回形如 `{question, multiSelect, options:[{label, description}], render_via, render_note}`，
把 `question` / `multiSelect` / `options` **原样**填进提问工具（WorkBuddy 里是 `AskUserQuestion`，
其它宿主用它的等价提问工具）即可成卡。

⚠️ 命令在 JSON 之后还会打印一段编号文字，**那不是给陛下的话术**，只是宿主没有选项卡片时的降级兜底——粘出去就等于又让陛下打字。

> 这段机制跟着数据走（`render_via` 写在返回里），不只写在文档里。原因见 `docs/TESTING.md`：
> 曾经只写在 `references/voice.md`，而主文件第一步又注明"不用额外读"，结果严格照主文件执行
> 恰好读不到机制，把选项念成了"陛下可回复：A／B／C"。

### 明确不做的

静默下单 · 自动提交订单 · **自动付款** · 自动填备注 · 取餐柜二维码 · 沟通卡 · 用黄道吉日判断是否消费 · 独立网页/复杂前端 · **未经确认的自动领券** · **未经三重复述的下单**。

### 写操作分级治理

| 档位 | 工具 | 规则 |
|---|---|---|
| **NEVER 永不执行** | 抽奖 | 消耗账号资产且无撤销路径，**任何情况下都不执行** |
| **CONFIRM 确认后执行** | 领券 / 创建配送地址 / 取消订单 | 免费或可撤销。臣**逐字复述** → 陛下明示 → 才执行 |
| **CONFIRM_STRICT 三重复述后执行** | 下单 / 团餐下单 / 商城下单 | **订单内容 / 金额明细 / 交付方式**三项全部点头才出单，且**只出待支付单、绝不付款** |

把领券和下单混为一档"一律禁止"是偷懒：两者风险量级完全不同。
关键在于——官方 `create-order` 创建的是**待支付订单**，官方声明的下一步是让用户扫码或用 App 付款，
**「创建订单」与「付款」是两件事**，不该同等对待。
分级之后陛下不必再自己打开小程序领券、也不必照抄菜单去下单，
但**不静默下单、不代付款**这两条底线**一条没动**。

## 四、安装与使用

### 前置条件
- Python 3.9+（**Skill 运行时只用标准库**，无需 pip 安装任何东西）
- 麦当劳 MCP Token，并在 WorkBuddy 中启用 `mcd-mcp`

### MCP 配置
复制 `mcp-config.example.json`，把 `YOUR_MCP_TOKEN` 换成你自己的 Token：
```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer YOUR_MCP_TOKEN"
      }
    }
  }
}
```
> 不要把真实 Token 提交到 GitHub。

### 直接跑
```bash
# 今日主题
python scripts/imperial_kitchen.py theme

# 指定日期演示（会标注「指定日期模拟」）
python scripts/imperial_kitchen.py theme --date 2026-10-23

# 用真实菜单筛选（budget_max / likes / dislikes / priority）
python scripts/imperial_kitchen.py match --menu tests/fixtures/menu_real_sample.json \
  --request '{"budget_max":30,"likes":["汉堡"]}'

# 官方核价核验
python scripts/imperial_kitchen.py verify-price --verified tests/fixtures/price_real_sample.json

# 完整奏折
python scripts/imperial_kitchen.py render --date 2026-10-23 \
  --menu tests/fixtures/menu_real_sample.json \
  --campaigns tests/fixtures/campaign_real_sample.json \
  --request '{"budget_max":30,"likes":["汉堡"]}'
```

### 跑测试
```bash
python tests/test_imperial_kitchen.py
# 或 python -m unittest discover -s tests -v
```

## 七、已实现与未实现

### 已实现并验证
- 八模块全部落地，60 项测试通过
- 真实 MCP 调用：`query-nearby-stores`、`query-meals`、`query-store-coupons`、`query-my-coupons`、`calculate-price`、`campaign-calendar`、`delivery-query-addresses`（详见 `MCP_INTEGRATION.md`）
- 场景路由：到店自取 / 麦乐送外送 / 得来速 / 团餐，参数与调用链按官方真实约束编排
- 节气/节日数据与权威来源交叉校验
- 合规自检（夸大表述、运势吉凶词）

### 麦乐送外送（2026-10-22 已端到端实跑验证 ✅）
全链路真实打通，并取得**配送费与打包费的真实数据**：

| 环节 | 真实结果 |
|---|---|
| `delivery-query-addresses` | ✅ 取到 `addressId` |
| `delivery-query-stores`（beType=2） | ✅ 3 家可配送门店 + `beCode` |
| `query-meals`（beType=2） | ✅ 外送菜单（**价格与到店不同**：巨无霸到店 26.5 / 外送 28.5） |
| `calculate-price`（beType=2） | ✅ 餐品 44.00 + 配送费 6.00 + 打包费 1.90 = **51.90 元** |

同一组合到店自取官方核价 41.00 元，外送 51.90 元，**高出 10.90 元**——这就是本项目区分场景口径的实际价值。

### 到店自取：就近靠关键词，不靠 IP（2026-10-22 实跑核实 ✅）

陛下提问："agent 能不能根据 IP 自行判断最近门店？" 答案是**不必，且臣也拿不到 IP**。
实跑发现官方返回里**自带 `distance`（米），且已由近及远排序**，而它算的是
**关键词的地理位置**，不是用户位置：

| `city` | `keyword` | 精度 | 最近门店 | `distance` |
|---|---|---|---|---|
| 杭州 | `西湖区` | 区县 | 麦当劳杭州灵隐景区餐厅 | 2545 米 |
| 杭州 | `黄龙体育中心` | 地标 | 麦当劳杭州西湖区玉古路餐厅 | 188 米 |
| 杭州 | `天目山路148号` | **街道门牌** | 麦当劳杭州黄龙世纪广场餐厅 | 410 米 |

（三行是**同一个查询点**下的实测：`天目山路148号`——浙大玉泉校区正门，一个公开门牌；
本文档不引用任何真实用户地址，任何人都能原样复跑这三行。）

⚠️ **区县一级不能拿来当"就近"**——同一个点，只报「西湖区」被送到 **2545 米外**的区中心，
报到地标或门牌只有 **188–410 米**，**差 13.5 倍**。地标与门牌谁更近取决于门店实际开在哪，
两者都算"就近"；**真正的陷阱是区县一级**。
因此引擎把地址一路切到**路名 + 门牌号**，`keyword_level` 分四级
（`street` / `landmark` / `district` / `city`），后两级标 `coarse_keyword=True`：
届时臣会明说"区中心离陛下可能很远"，并把「给个更准的地标」排到第一位，
而不是拿一个偏远结果硬说是"陛下附近的门店"。

其余口径：以陛下**外送收货地**为默认来源（须标明非实时定位、也未必是陛下此刻所在），
陛下说出更具体地标时优先用陛下的；展示时如实带上官方距离与完整 `storeCode`；
**最近那家超过 1.5 公里**就主动提示换关键词；`distance` 缺失时显示"距离官方未返回"。

### 已实现但未充分验证
- **优惠券匹配与核价（本单可用券）**：**已用真实券验证**（2026-10-22）。代领券后 `query-store-coupons` 首次返回非空（2 张），
  并用**两次官方核价**对比验证券效：麦辣鸡腿汉堡券 `discount` 13.60 元 → 应付 19.00 元；王牌炸鸡任选2 券 `discount` 10.10 元 → 应付 27.80 元。
  ⚠️ 仍未验证：多券叠加规则（本轮只做了单券核价）。
  ⚠️ 实测异常未下断言：商品 `1440` 不带券时官方核不出价（已用 `901100` 对照排除接口故障，官方未说明原因）。
- **可领取券令与代领**：`available-coupons` 真实返回 3 张券（11.9元麦辣鸡腿堡 / 19.9元王牌炸鸡任选2 / 免费脆薯饼），解析与展示**已验证**。
  陛下说「帮我领券」时臣**可代领**，但必须**逐张复述券名 + 获明示确认**后才执行，且领完要回查卡包、再核价。
  ⚠️ **官方硬限制**：该工具**只能一键全领，不支持指定单张**（无 couponId 入参），臣如实说明，不假称能挑。
  ⚠️ 臣**未核实**领券是否消耗领取资格或次数（官方声明未提及）。
- **起送价**：麦乐送外送不设起送门槛（陛下明示；官方返回中亦无该字段）。
  奏折只作一句说明，**不给金额、不标"未能核实"**。

### 为什么拆成「核心 + 按需」

原 `SKILL.md` 单体 538 行 / 17,850 字符 ≈ **10,670 token**，七步流程全部一次性注入；
模型读到完整说明书，往往一路跑到第七步才回话——陛下实测首响要等二三十分钟。

改为渐进式披露后：**首响只需读核心（≈3,042 token，-71%）**，
且核心里写明「呈上四项后本轮到此为止，陛下点选前不得读 `workflow/`、不得调 MCP」。
结构由测试 160–164 守卫：核心不许再膨胀、停下指令不许被删、子文件不许失联。
